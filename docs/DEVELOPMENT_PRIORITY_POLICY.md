# 跨项目开发优先级与阶段换向规范

> 适用于本仓库的 AI / Codex / 自动化开发工作。目标：交付实际可用的功能，而不是无限优化某个技术模块。版本：2026-10-15。

## 一、解释「继续」

「继续」默认要求重新评估**项目整体下一步的最高价值工作**，不是无条件延续上一个 PR 的技术方向。先读最新源码、已存在的项目约定、路线图、Draft PR、CI/Runner 和并行开发状况；不要凭交接记录猜测当前状态。

以下推断均不成立：
- 上一轮修的模块天然比其他模块更重要。
- 测试数量、覆盖率、PR 数量增长本身代表用户价值。
- 某功能还存在理论风险，就必须先处理全部假设边界才能开发其他功能。
- 被外部接口阻塞时，应该无限提前构建兼容层、审计体系或测试模拟器。

## 二、每轮评估三个问题

1. **真实阻断是什么？** 有复现、日志、用户反馈、具体威胁模型或明确发布门禁吗？真正的数据丢失、严重安全问题、核心功能不可用优先处理。
2. **下一轮能让用户更接近可用吗？** 具体改善哪个实际操作、页面、平台、交付里程碑或确定的问题？如果答案只是“新增若干测试”，应重新排序。
3. **是否受外部依赖限制？** 上游 API、验证过的设备身份、用户决策或构建环境尚未到位时，先冻结依赖链并转做独立可交付的核心任务。

## 三、优先级

| 优先级 | 适用工作 |
| --- | --- |
| P0 | 已知严重安全或数据破坏风险、真实用户数据串号、核心功能阻断、可复现重大崩溃 |
| P1 | 用户能感知的主流程闭环、关键易用性、核心功能真正可体验或可交付 |
| P2 | 明确存在的构建/集成/发布门禁、平台真机验收、确定的外部接口对接 |
| P3 | 针对已识别的高影响风险进行必要防御、精准回归测试 |
| P4 | 没有当前用户场景的假设性边角、重复审计、无界架构扩展 |

优先级需结合用户目标、影响范围、成本和时机调整。不能因排序规则忽略真正的 P0 风险。

## 四、必须停止并重新排序的信号

以下任一成立，下一轮必须先复盘，不得惯性继续原模块：

- **连续两轮**主要补理论性异常、测试或内部审计，但没有推进实际用户流程。
- 当前模块依赖尚未交付的外部接口，下一项工作仍无法接入真实功能。
- 本阶段已满足预先定义的验收门槛，只是为了「更完美」继续扩展。
- 进展只能用通过测试数、新类数、PR 数量衡量，难以说明实际收益。
- 另一个核心功能明显更有价值，并且可在现有条件下独立推进。

复盘之后明确选一项：**继续（给出依据）／收口冻结／转向更高价值工作／等待上游**。不必向用户反复呈现冗长评分表，但需要能清楚说明选择依据。

## 五、任务开始和完成标准

开始一阶段时明确：用户价值、完成范围、必要的自动/人工验收、暂不做的内容、外部依赖和停止条件。优先复用成熟实现，不为简单问题新建复杂框架。

阶段结束必须严格区分：
- **代码实现完成**：已有源码，不代表通过验证。
- **自动化验收通过**：精确被测源码、测试范围和限制有证据。
- **功能真正可用**：实际用户主流程已经接入，不是只有实验 flag 或 mock。
- **真实平台／跨设备验收**：有真实环境证据，不能用模拟测试替代。

完整验收后不机械追加下一层防御 PR。一个阶段应尽量控制 PR 数量和人工验收次数，优先做端到端闭环。

## 六、持续开发时的简短判断模板

> 当前最值得做：【明确的真实问题或用户流程】  
> 为什么胜过继续旧模块：【收益、依赖和机会成本】  
> 本轮完成标准：【可验证的结果】  
> 刻意不做：【无界优化或仍被外部阻塞的部分】  
> 结束决定：【继续／冻结／换向／等待】

## 七、现有规则不得覆盖

本规范**只约束开发优先级**。项目现有的 `AGENTS.md`、安全指南、分支保护、Release、自动化测试、数据隐私与 CI 限制继续适用；更严格的安全约束优先。不得为追求快速交付而绕过真实性验收、授权或回滚措施。

当用户明确指定继续一个模块时可以继续；但仍应主动提示该方向的机会成本及阻断，不陷入无界循环。
